# Solvys Operations Handbook

Version: 1.0
Factory sprint: S011 - Solvys Factory Operating System and Cutover
Authority: TP and the accepted Solvys Factory operating record
Scope: every Solvys internal product, client project, planning task, implementation task, automation, and handoff

## Purpose

The Solvys Factory keeps planning, product management, development, provider work, documentation, proof, and communication in one operating chain. Agents use this Handbook when they enter a project, lose context, encounter drift, or prepare a handoff.

The Factory exists because a passing test cannot prove that a product works. A feature can have source code and green tests while its bucket, token, queue, provider, route, or button remains disconnected. The Factory maps and proves the full reaction chain.

## Operating language

- **Cabinet:** accepted operating truth, decisions, manifests, receipts, and source pointers.
- **Codebase:** repository source and code-bound contracts.
- **Dyno:** the backend proof lane. It tests the engine before the body depends on it.
- **Chassis:** frontend routes, screens, states, navigation, and control relationships.
- **Control inventory:** the direct record of which button does what.
- **Fluid stack:** the reusable Solvys default built from the proven provider estate.
- **Dynamic stack:** an approved project exception caused by performance, security, hosting, integration, cost, or exit needs.
- **Proof rung:** the highest reality level that evidence reached.
- **Sprint Unit:** one visible orchestration task plus its visible implementation tasks.
- **Entrance receipt:** proof that a task read the correct signs and verified current custody before work.
- **Comrade care:** repairing shared access, path, connection, or context defects for active sprint work.
- **Infraction ledger:** the per-project record of repeated operational failures, their evidence, counts, owners, and repairs.

The Solvys Build Kit is the shared UI assembly source. Load its source-copied
presets when a project needs the Interview, Architecture Canvas, control
inventory, state, Outputs & Sources rail, or workbench assemblies. Keep retired
visual-editor exports outside the Factory source until TP records a deliberate
source transfer with provenance and proof requirements.

## The Factory entrance

Before substantial work:

1. Read the project `WELCOME.md`.
2. Read the sign for the assigned lane: PL, PM, DEV, or CAO.
3. Read `project-manifest.yaml`, the active sprint record, and the latest accepted receipt.
4. Verify repository, branch, SHA, dirty ownership, Cloud environment, SSH route, provider environment, and account.
5. Search the project Paste folder and approved Building Block pinboards.
6. Read the project `infraction-ledger.json` and include its open count in the entrance receipt.
7. Record an `entrance-receipt.json` before changing product state.

Do not restart product implementation from a stale chat summary. Walk back through the entrance.

## PL: Product Lifecycle

### PL0: Outcome and authority

Define the original problem, outcome-owned solution, client identity, decision owner, cost boundary, performance target, security needs, hosting model, integrations, exit plan, acceptance criteria, and protected zones.

### PL1: Approved foundation

Inspect repository truth, run the Stack Interview Wizard, search Paste, select the fluid and dynamic stack, verify OSS and approved UI libraries, and install eligible foundations first. Load the accepted Solvys Build Kit preset when the project needs shared interview, architecture, control-inventory, state, rail, or workbench assemblies. Record its version, destination, product-owned seams, and proof receipt.

All proven Solvys architecture is eligible precedent. Prefer a verified working seam for a simple job before creating another version of it.

### PL2: Contracts and ownership

Complete the backend Architecture Canvas, provider-resource map, data contracts, permissions, frontend navigation, control inventory, environment plan, proof gates, protected zones, and ownership.

Invoke the Kirby interface inventory process for a full baseline, sprint delta, and phase-gate rebuild. Store the accepted report as the comparison product for UX, UI, product-loop, feature-creep, and technical-debt checks.

### PL3: Backend dyno proof

Provision and connect the real backend resources. Test load, failure, authentication, queues, storage, tenancy, retries, observability, and rollback against the numeric power target declared by the project.

Backend comes before dependent frontend completion. A chassis can be designed in parallel, but it cannot pass acceptance while its engine resource is missing.

### PL4: Chassis integration

Build Wonder proposals against accepted contracts. Preserve each screen, route, state, control, responsive behavior, and navigation relationship.

Run two-stage control validation:

1. Confirm that the control exists at the accepted Wonder target and ChatGPT Site route.
2. Confirm that its complete feature path reaches the correct backend, permission, provider resource, state change, and proof.

An emergency frontend repair may restore service first. Update Wonder, the control inventory, the Site, and the Cabinet before closure.

### PL5: Release and handoff

Deploy from the accepted checkpoint. Prove the intended live environment. Update each document, canvas, Linear record, and receipt. Send the Slack receipt through the project identity. Close task-owned processes and leave the workspace clean.

## PM: Product Management

PM work uses four durable responsibility categories:

1. **Product and scope control:** PRDs, requirements translation, Stack Interview decisions, scope, Linear, and OpenProject migration.
2. **Architecture and integration control:** backend-to-frontend contracts, provider resources, environment ownership, documents, and canvases.
3. **Quality and reliability control:** code sanitation, hardening, performance, debugging plans, proof quality, and technical debt.
4. **Delivery and communication control:** sprint receipts, Slack updates, release readiness, adoption, customer success, and ROI evidence.

Internal products can use one automation per PM category. External projects use one Master PM automation unless TP approves another operating shape. Do not create a swarm of small management automations.

## DEV: Development

### Do

- Verify repository, branch, SHA, local path, Cloud environment, SSH route, provider environment, and dirty-state ownership.
- Search Paste and approved references. Gather and install suitable foundations first.
- Repair safe shared connection defects for active sprint comrades. Update only active tasks that have no unread TP message.
- Build backend contracts and provider resources before dependent frontend completion.
- Run load, failure, auth, queue, storage, tenancy, retry, observability, and rollback checks against the declared power target.
- Build Wonder proposals in parallel against accepted contracts.
- Preserve every route, state, control, responsive behavior, and navigation relationship.
- Record the direct function of every button.
- Fix the earliest shared cause when several paths fail. Show the cause as a node map and explain it with a car-system metaphor.
- Remove obsolete code after ownership, recovery, and reference checks.

### Do not

- Treat green tests as production completion.
- Build dead controls, placeholder APIs, decorative OAuth, or unprovisioned storage.
- Invent provider IDs, secrets, environment state, user data, metrics, or acceptance marks.
- ask TP to make ordinary implementation decisions that current truth can answer.
- Stop at the first login page. Follow the authorization chain.
- Mutate unknown dirty work, reset accepted history, or delete quarantine resources.
- Restart another task's operation without its entrance receipt and TP's requested cue.

## CAO: Executive Operations

The CAO maintains the cross-project priority map, dependencies, cost, ownership, proof, and stress signals. It starts from current truth, applies the Stack Interview and Ponytail chain, assigns protected zones, fixes the earliest shared seam, and keeps the sprint aligned to the accepted outcome.

Ordinary operational friction triggers recovery work. Escalation begins when a choice changes client identity, cost, rights, secrets, destructive state, billing, or irreversible provider behavior.

The CAO uses visible green and red node maps. Green means the node reached its declared proof rung. Red names the earliest failed or missing dependency.

## Infractions and death-loop repair

The exact phrase `infraction committed` is an operational write trigger. The
agent that uses it records the infraction immediately in the active project's
`infraction-ledger.json` with a short mechanism title, category, severity,
evidence, source task or automation, owner, and next action. The bundled
`scripts/record_infraction.py` merges a matching fingerprint and increments its
count. It never stores secret values or developer names.

Use `category: automation-death-loop` and `--death-loop` when an automation or
agent repeats the same action without new evidence or progress. The second
repeat in one work window is a stop signal. Stop the repeated action, preserve
the current evidence, fix the earliest shared cause, and record the repair
before retrying.

The 7:00 AM daily sitrep includes every registered project's open ledger. The
CAO reviews recurring and high-severity entries first, assigns one owner and
one next action, links the repair receipt, and closes or escalates the entry.
An unchanged entry produces no user-facing update. It remains in the ledger
until its status changes or a human gate is recorded.
Use `python3 scripts/sweep_infractions.py` to build the ranked read-only repair
queue, and treat any invalid ledger in its output as a control-plane defect.

## Stack Interview contract

Every large plan starts with the Stack Interview Wizard. It records:

- Fluid-stack defaults
- Dynamic-stack exceptions
- Numeric performance target
- Security and compliance needs
- Hosting model
- Integrations
- Operating cost
- Exit plan

The interview exports into the Cabinet, PRD, Architecture Canvas, provider-resource manifest, sprint plan, Outputs & Sources, and control inventory.

For a multi-track sprint, the Sprint Unit Head selects the smallest decision-complete question set. Use all 21 questions when 21 material choices can change scope, cost, authority, architecture, or acceptance. Record why a smaller set is complete.

## Fluid stack and dynamic exceptions

The fluid estate uses Cloudflare, Vercel, Fly.io, Supabase, and PostHog in proven roles. The default documentation publication layer is Mintlify. Linear remains the issue authority until Solvys-2 and OpenProject pass the migration gate.

Dynamic exceptions include Hono with FastAPI workers, Authentik or Keycloak, database-per-customer isolation, Docling with OpenFGA, OpenTofu customer environments, OpenTelemetry, Unleash, Docusaurus portals, Metabase, and other approved project-specific needs.

Every exception records license, security, support, migration, exit, operating cost, and owner.

## Control inventory

Every interactive control records:

- Surface, route, and state
- Wonder source node
- ChatGPT Site route
- Event and client handler
- API route and backend handler
- Authentication and permission gate
- Database, queue, bucket, or provider resource
- State change and user feedback
- Loading, disabled, empty, error, and recovery states
- Linear issue and documentation link
- Required proof rung and current proof

Broken controls become red nodes and receive an issue or sprint owner.

## Proof ladder

Use separate proof rungs:

`source -> static checks -> tests -> runtime -> provider -> deployed -> installed -> human accepted`

A receipt names the exact rung. A lower rung cannot mark a higher rung complete.

## Skill extraction trigger

The directive `skill that` is a case-insensitive write trigger. It turns a
roadblock into a reusable skill record and a validated guardrail. The active
owner writes `Skills/Proposals/<date>-<slug>.md` in the protected project
Cabinet using `factory/Factory Registry/Templates/skill-proposal.md`, searches
the existing suite and approved Paste sources, then patches the smallest fitting
skill or creates a new one under the `skill-creator` rules. A new skill uses the
`init_skill.py` path before its `SKILL.md` is edited. The proposal records the
mechanism, failed guardrail, reusable procedure, do and do-not rules, proof test,
owner, protected zones, and next gate. It contains no secrets or raw client
session data.

## Breakthrough records

The exact direction `Update the C-Cab with that Breakthrough` is a durable
learning write trigger. The active owner writes
`Breakthroughs/<date>-<slug>.md` in the protected project Cabinet using
`factory/Factory Registry/Templates/breakthrough-record.md`, reads it back, and
routes the lesson to the smallest layer that prevents recurrence:

- universal process: Handbook, agent prompt, or Factory sign;
- repeatable workflow: existing skill or a new validated skill;
- project-specific behavior: Welcome Mat, manifest, Architecture Canvas, Design
  canon, or repository instructions;
- temporary state: infraction ledger, Sprint Unit, or receipt;
- explicit Codex-memory promotion: one concise ad-hoc note under
  `/Users/tifos/.codex/memories/extensions/ad_hoc/notes/`.

Record the trigger, mechanism, failed guardrail, prevention rule, proof and
readback, protected zones, owner, changed records, and next gate. Link the entry
from the active Sprint Unit or latest receipt. Keep secrets, browser session
data, transcript dumps, and unnecessary client identity out of the record. A
blocked write remains pending evidence and cannot mark acceptance.

For authenticated provider surfaces, a semantic DOM or accessibility probe can
miss the visible application shell. When that probe conflicts with the
authorized visible UI, preserve the tab and perform the smallest scoped visual
check before classifying provider state. Record only the required label match or
mismatch. Do not inspect browser storage, cookies, session data, group
membership, credentials, or unrelated visible content.

## Sprint Units and model lanes

- Sol High owns Sprint Unit orchestration, architecture, dependency control, and acceptance.
- Luna Max owns most implementation, routine planning, review, and voice work.
- Terra Extra High owns heavy implementation, deep debugging, migrations, and complex systems work.

Implementation occurs in visible Full Access tasks. The head can create the task or supply a complete Launch Card for TP to paste. Hidden subagents do not implement product work.

## Work-window grounding

Each active-goal task uses a 120-minute window:

1. Start with an entrance receipt.
2. At 90 minutes, write a grounded checkpoint.
3. At 120 minutes, stop and post a complete rollover prompt in the current chat.
4. Start a new task automatically only after Full Access is verified.
5. Otherwise, wait for TP to paste the rollover prompt.

A long-running orchestrator can own a sprint for up to 24 hours through at most twelve grounded windows. Active Sprint Units refresh at 7:00 AM America/New_York with a daily sitrep as the first message.

## Memory and storage

Keep the working context between 60 and 80 percent when the task exposes that measure. Store durable evidence in the Cabinet and load only the Welcome Mat, active sprint, exact source pointers, and latest receipt.

The Daily Storage Runner operates at 2:15 AM America/New_York and after task-refresh events. It protects active work, current or pinned tasks, open handles, dirty repositories, unknown ownership, credentials, recovery state, Cloud transport, and uploads.

At less than 10 GB or 5 percent free internal capacity, block new local checkouts, dependency stores, builds, previews, and servers. Use repository-backed Cloud work.

## Git and custody

- `main` stays clean, protected, and deployable.
- The daily integration branch is `YYYY-MM-DD`.
- Cloud checkpoint refs use `refs/sprints/S###/T##/P##`.
- Human-facing work titles use `MM/DD vX.Y.Z: three words`.
- PR titles use `S### - concise context`.
- Squash at the PR boundary.
- Never force-push accepted history.
- Midnight staleness produces a receipt and rollover.

Every non-trivial commit body states outcome, principal areas, proof, protected zones, and remaining handoff.

## Authorization chain

Use this order:

`Paste project folder -> regular Chrome for Google Sign-In and project password -> Google Continue -> provider Allow access -> Codex in-app browser or Chrome Dev for the authorized target -> local CLI or credential store -> TP MFA approval`

The agent enters known credentials in regular Chrome. It never enters the project
password in Chrome Dev. It opens the exact approval page, selects **Continue**
and **Allow access**, then uses the authorized target session. Ask TP for the tap,
code, or digits at the time they are needed. Continue other safe work while
approval is pending.

Project Google accounts control provider registrations unless a project manifest states an exception. GitHub uses the verified owner lane.

## Communication

Use the project Slack workspace when available. Authenticate through the project Google identity. Use browser login when a connector opens the wrong workspace.

Use the word `collaborative` when several people worked on a sprint. Do not preserve stale developer names in recurring plans or automation prompts.

Send Slack receipts after proof. Include outcome, scope, proof rung, environment, remaining human gate, and next action.

## Google Drive Solvys Custody

Use `Solvys Custody/<Project>/S###/{Inputs,Working,Accepted,Handoffs}` for large evidence, provider exports, accepted media, Google-native collaboration, and handoffs.

Do not store code or secrets there. The Cabinet stores the Drive identifier, owner, purpose, hash when applicable, and linked sprint receipt.

## Weekly Factory review

The Sunday 7:00 AM review produces the Factory sitrep, active Sprint Unit status, automation health, memory and capacity state, recurring operational failures, and accepted process changes.

The private stress report can count profanity in TP's original task messages, group the causes, and produce a PDF chart. It focuses on operational causes and process repair. It does not score collaborators.

## Closure

Before closure:

- Verify the declared proof rung.
- Update Cabinet, repository contracts, Mintlify, Linear, canvases, and control inventory as applicable.
- Reconcile Wonder and ChatGPT Site state for frontend work.
- Close task-owned processes.
- Record protected and quarantined state.
- Return the exact next action.
