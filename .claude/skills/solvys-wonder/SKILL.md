# Solvys Wonder

## Authority and required routing

Owner direction, October 14, 2026: once a base has been handed to Sam for frontend polish and second pass, **Frontend Wonderer is the only agent role authorized to decide how that frontend looks**. Sam, the human Super, retains final authority. The role works in the project's actual external Wonder worktree and its bound file. Preserve that worktree, sessions, dirty files and the owner's edits.

Every Foreman, developer, Implementer, Integrator, Reviewer and Solver reads this skill before frontend work. They implement or verify the Wonderer's current brief; they do not introduce their own visual interpretation, redesign, token system, component replacement, layout or parallel UI. A code or production snapshot establishes the starting base, not permission to overwrite later owner polish. Backend behavior, permissions and domain contracts remain owned by the product repository.

Before base handoff, construct only the authorized base from the actual repository and accepted sources. Record the handoff revision and scope. After handoff, visual changes go through the Wonderer and the owner. A bug fix that restores the approved look can follow the brief; a fix that changes the look requires the Wonderer's updated direction. When a brief conflicts with an owner correction, preserve the owner correction and return the mismatch to the Wonderer.

Task/project tracking uses Goalpost-in-gpt connectors. Reuse actual project/issue IDs, revisions and native execution-session references; read back writes. Do not invent a second progress ledger or claim unavailable connector access.

## Export-first guidance and consultation

Use the Wonderer's committed or locally linked exports and compilation/import instructions first. These normally exist at session start; locate and read the current project-matching handoff before seeking fresh guidance. Existing complete instructions do not require contacting the author again. If clarification is necessary, consult the Wonderer through its existing Codex session or native provider terminal, not through Wonder. Wonder remains the design/import/Preview surface, not the agent-consultation channel. Resolve the most recent project-matching external worktree and its instruction pointers before asking the owner for session identity; verify repository/source mapping and revision rather than selecting by timestamp alone.

## Current Wonder surfaces

Platform capabilities were checked against Wonder's current product information on October 14, 2026. Treat per-organization availability, current controls and account access as live facts to inspect again.

- **Desktop Sessions** holds connected repositories, worktrees and their chats. It can connect GitHub or add an existing local folder. Reuse the registered external worktree; do not clone a replacement because a path is unfamiliar.
- **External Chat** lets the owner work with a session from the canvas. Confirm the exact repository, worktree, chat, file branch and page. A Wonder file branch and a Git branch are different identities.
- A worktree agent can edit source and canvas using its own environment. The in-app assistant's source-change plan is not evidence that repository files were changed. Do not confuse these surfaces.
- **Changes** and **Terminal** expose worktree source and commands. Inspect actual staged, unstaged and committed work before compilation or import. Preserve other agents' and the owner's changes.
- A managed dev server belongs to a specific worktree and port. Its **Preview** is bound to that server. Starting another shell server or opening localhost does not prove the correct managed Preview. Inspect the live Preview control and logs; use the user-owned start flow when required by the current app.
- The platform's current desktop chat prerequisites may differ from the Factory's authorized model and subscription route. Verify actual harness/account availability; do not switch providers, buy credits or treat a product capability as spending authority.

Read live product information and exposed capabilities before relying on old UI labels. Do not impose old canvas-only assumptions on external worktree sessions. No invented menu, import command, callback or active session.

## Enter with custody

1. Read the project Welcome Mat or registered onboarding composite, team/project manifestos, canonical PROJECT-STATE.md, latest receipt and current owner scope.
2. Verify repository origin, Git branch/SHA, external worktree path, dirty ownership, native session, Wonder organization/file branch/page, protected regions and current brief revision.
3. Read the live source and design before changing them. Reuse authenticated access. Never replace the user's exact context with a scratch project or a screenshot approximation.
4. Route login and reauthentication to Solver using the approved credential skill. A local Foreman may perform authorized key generation and configuration directly when its existing connections permit; verify the actual account/project scopes and result. Escalate insufficient access or three unsuccessful attempts to Solver. Keep credentials out of briefs, chat, logs and source. Retain Paste if used and preserve authorized browser sessions.
5. Keep canvas, source, compilation, managed Preview, deployment and human acceptance evidence separate.

A missing connector does not erase an existing authorized desktop session. Inspect supported current capabilities and use only the authorized surface. If no write path exists, continue read-only inspection and escalate the specific access gap; never fabricate synchronization.

## The Wonderer brief or sprint is mandatory

The Wonderer always sends a revision-bound brief or sprint for other Factory agents to use. Use [the handoff template](references/frontend-handoff.md). Put it in the existing project sprint/brief location and link it from the existing project state and Goalpost issue. Do not create a second editable status authority.

The brief must include:

- owner handoff point and accepted base SHA; current source SHA, Git branch, dirty custody and exact external worktree;
- actual Wonder file branch/page/artboard or Preview identity, session reference and visible owner corrections;
- exact affected files, component/source mapping, tokens, assets, states, breakpoints and protected regions;
- **compilation instructions**: actual package manager, installed tool versions, working directory, setup/build/test commands, required environment variable names only, output paths and expected results;
- **import instructions**: actual source/artifact, destination, dependency order, current supported import mechanism, mappings, managed server/Preview binding, and commands or UI steps verified for this project;
- integration constraints for other agents, allowed nonvisual changes, acceptance checks and rollback/recovery reference;
- brief revision, author role/session, recipient role/session, actual Goalpost issue/revision, known gaps and evidence links.

The receiving agent reads the exported brief and records the exact path and revision before dependent frontend implementation; this does not require a new author conversation. If compilation or import instructions are absent, stale or fail against the named revision, send the exact failure to the Wonderer. Do not guess replacement steps or redesign around it. The brief itself does not authorize a merge, deployment, purchase or account change beyond current owner scope.

## Compile, import and verify without visual drift

1. Inspect actual package scripts and dependencies. Install or compile through the existing project toolchain; never hand-build substitutes.
2. Follow the brief's source mapping and preserve owner edits. Integrators reconcile functional changes with the Wonderer rather than overwriting frontend files wholesale.
3. Import through the current verified mechanism. Distinguish native editable component trees from bitmap captures and a server-bound Preview. None is interchangeable proof of the others.
4. For code-linked designs, preserve bindings and source provenance. For unbound substantive design changes, preserve the original and work on an authorized copy unless the owner explicitly requests in-place editing. Do not duplicate bound source away from its mapping.
5. Treat old IR-specific restrictions as applicable only when the selected import tool actually imposes them. Never rewrite an existing React frontend solely to satisfy a guessed canvas restriction. Inspect the current import capability and error before changing source.
6. Compare the Wonderer-approved revision and target at matching route, viewport, data/state and theme. Check typography, geometry, spacing, colors, interaction states, responsive behavior and accessibility. Report actual differences to the Wonderer.
7. Verify compilation, import, source mapping, managed Preview and functional integration separately. Review validates the brief; it cannot overrule the Wonderer with a new design preference. Sam accepts the polish and second pass.
8. Close every canvas edit batch through the current supported completion flow. Inspection alone needs no edit-completion claim. Preserve the authenticated context and all unrelated work.

## Attempts, escalation and acceptance

Use the shared Factory `workflow/roles.md` and completion hooks. After three unsuccessful attempts at the same obstacle, stop repeating the approach and escalate with the brief/issue revision, evidence, attempted fixes and exact decision needed. Frontend visual decisions go to Frontend Wonderer. Authentication goes to Solver; a local Foreman may complete authorized key-generation/configuration work when its connections permit, with the same three-attempt escalation limit. Working agents report operational blockers to Foreman; completion disputes go to Reviewer. Foreman reports to Solver; Solver contacts Sam as Super when recovery fails or human-only input is required. Never pretend a handoff was delivered without an actual recipient and readback.

Preserve explicit pauses. Review requests preceding a goal pause for separately authorized work, but do not resume the paused goal or evade its scope. No hook grants new authority.

Before completion, reread owner corrections and both manifestos. Verify the full approved journey against the same brief and source revision, include relevant rendered evidence, and identify any deviation. Passing compilation, a source export, or a screenshot alone does not establish accepted frontend polish, import success, deployment or runtime behavior.
